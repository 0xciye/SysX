# SysX

> **Current availability:** Pixel Seek is the only usable detection engine. Object Detection and its ONNX Runtime, OpenVINO and TensorRT integrations are **not ready for use**. Their source/dependencies remain for development; build and unit-test results are not functional validation. SysX supports **Medius only** through its Rust SDK.

SysX is a portable Windows desktop application distributed as one `SysX.exe`; no installer is produced. The executable embeds its Rust backend and web UI assets, then extracts them to app data while it runs. The receiver window is a compact monitor — Preview, five equal-width Mouse State buttons, device state, and receiver connection state — shown as a chromeless Microsoft Edge app window (`--app`, with its own profile under app data) that loads the loopback page `/monitor.html`. Configuration opens automatically in a separate browser window at a loopback-only local address. Closing the receiver window shuts SysX down. Settings are stored in the computer's app-data folder and restored on launch. There are no Start, Pause, Stop, or Preview visibility controls.

The application source is Rust: a small native host (`src-tauri`) embeds and supervises the Rust backend sidecar and owns Medius device I/O; both the receiver monitor and the configuration page are the Leptos/WebAssembly UI served by the backend on loopback. Trunk builds that bundle. The former `eframe/egui` native window has been removed. The legacy React/TypeScript frontend and Python backend have been removed. Object Detection has development adapters for ONNX Runtime, OpenVINO and TensorRT; all are unavailable for use. Pixel Seek is the only usable engine.

## Current status (2026-10-16)

The active source and runtime are Rust across the native host, the Leptos/WASM monitor and config UI, and the receiver sidecar. The monitor (`/monitor.html`) is intentionally a single dark Preview page: a thin status bar showing the device state, a centered square feed of up to 640 × 640 px with an in-feed `resolution · FPS · ms` HUD plate, and a Mouse State row matching the feed width. The native host forwards device and button state to the page through the backend (`device_status` command → `state.device`). The loopback configuration page mounts the same Rust UI in the default browser and persists settings through `app-settings.json`. The OBS sender plugin in `obs-plugin/sysx-canvas-sender` is implemented; its destination IP/port are compile-time constants in `sysx_canvas_sender.cpp`; see its README. The design source of truth is [design-system/sysx-native-receiver/MASTER.md](design-system/sysx-native-receiver/MASTER.md). Windows executable and physical Medius behavior still require target-environment validation.

The desktop shell shows the always-visible Preview, Mouse State, device status, and receiver status. Preview displays “NO FRAME” while waiting for a sender and starts automatically when a valid frame arrives. The HUD contains only measured processing FPS, latency, and processing resolution. The circle-only FOV overlay is always enabled; its size is configured in the separate browser page and scales with the displayed image.

The local configuration page keeps General, target-relative X/Y offsets, X/Y smoothing Min/Max sliders (strength 1–50, drawn at random per target), Sensitivity, recoil, and the independent Auto trigger key/FOV controls plus Delay, Cooldown, and Sleep timing fields (milliseconds) together on one page. It starts with one `Default` profile and stores up to three independent profiles in `app-settings.json`; users can create, clone, rename, delete, and select them. A rising edge on the physical middle mouse button cycles through the profiles that exist and applies the selected profile immediately. Holding the button does not repeat the switch. The cards use a balanced three-column, two-row rectangle on wide desktop layouts, two columns at medium widths, and a stacked view when compact. Motion, Auto, and Recoil are enabled from the toggle group directly below Detection Engine. Trigger button can be set to Right, Middle, M4, or M5; Left is excluded. **Apply Changes** writes `app-settings.json` under app data and applies supported runtime settings immediately. The authenticated preview WebSocket also emits changed state snapshots while streaming, so the already-running native Receiver updates its FOV, preview scale, crop resolution, mode, telemetry, and error state without a restart. The backend loads that file on startup and creates it with defaults on first launch. Auto's detection frame publishes `auto_target_valid` only when the shared HSV mask reaches the screen-center cell inside the active Auto FOV; a colored pixel elsewhere in the FOV does not fire, and Auto does not rank that pixel, feed it into movement, or draw a target line/ring. Its isolated timing state starts Delay when a center-crossing target is first observed, starts Cooldown at the moment a left-click command is emitted, and uses Sleep only as the Auto polling cadence; Sleep is not added to Cooldown. Once Delay starts, the pending click survives the target leaving the center; further crossings do not restart that delay or queue extra clicks. Releasing the trigger, disabling Auto, or changing its timing cancels the pending click. After a click, target loss rearms the cycle. The action reaches Medius through `press/release(Button::LEFT)` on the existing type-0 serial queue. The selected physical trigger gates movement; the latest target is refreshed immediately while an independent 4 ms movement ticker continuously recomputes small deltas, recoil is added to Y, and each device command is clamped to ±32 per axis. The offset marker previews the signed crop-pixel destination relative to the selected target. Lower alpha filters more; `1.00` leaves the target unchanged. Movement uses the internal NCAF three-zone response, prediction, cubic Bézier response, and occasional micro-corrections. The filtered target is used separately from raw detections for Preview and movement. The page opens on an available local port beginning at `4201` if the preferred port is busy. Backend selects the model artifact; Compute is passed to the selected runtime where supported. Precision remains a saved preference because the imported artifact determines its precision.

The SysX mark is a custom crop-frame and focus-point SVG shared by the web config and desktop assets.

The backend tracks source and inference resolutions, actual inference device, detection counts, measured source/processing/preview FPS, processing latency, input/transport drops, and the active profile. The native monitor header shows the active profile name and updates it from the same state stream used by the config page. The native monitor HUD intentionally shows only processing FPS, latency, and processing resolution. Source FPS counts valid decoded frames; processing FPS counts completed detections. Both use a trailing one-second window. The processing-FPS window retains up to 4096 completion timestamps; a regression test verifies its count is not capped at 360 FPS (synthetic timestamps, not a throughput benchmark). The preview returns to its sender-waiting state and clears the old image and live measurements when the stream goes idle. Once its authenticated backend connection is ready, the status reports “Waiting for sender.” A circle-only FOV overlay is always visible; its size is adjustable from 1–360°. Its diameter scales with the shorter side of the displayed image, and 360° fits inside that image at any sender resolution. Motion and Auto use one shared RGB-to-HSV profile registry and the selected Motion target color. Auto has its own FOV, and while its enabled trigger is held the backend uses Auto's FOV and the monitor colors that FOV ring blue. When released, Motion's green ring and FOV return.

The monitor window opens at 720 × 820 and adapts down to phone-like widths (feed and Mouse State shrink together; the port label hides below 520 px). Screenshots in `design-review/` predate the web monitor and are not current UI references; the new monitor has not been visually captured yet.

An earlier release-mode validation app with isolated app data received the 192 × 192 JPEG fixture on UDP port `4202` during an 8-second 360-FPS-target run. The sender measured 350.74 FPS and skipped 74 sender slots; the HUD showed 355.0 source/processing FPS, 60.0 preview FPS, 0 input/transport drops, and 0.04 ms processing latency. This is historical pre-Rust performance evidence; it does not validate the current Rust path, OBS, Windows, sustained sender throughput at 360 FPS, or target hardware.

Rust UI unit tests cover aspect-preserving preview scaling, letterboxed detection-box mapping, and HiDPI canvas sizing. Rust backend tests cover detection confidence, target selection, committing the ONNX/TensorRT/OpenVINO model bundle, and changing the UDP port then processing the actual JPEG fixture on the new port.

The unavailable Object Detection development path accepts one bundle containing `.onnx`, `.engine` or `.plan`, and an OpenVINO `.xml`/`.bin` pair. The ONNX Runtime adapter targets CPU; OpenVINO accepts CPU/GPU/NPU targets supported by the installed runtime; TensorRT is built only when TensorRT headers and `CUDA_PATH` are available and requires a GPU engine. The exported YOLOv8 model must accept NCHW RGB float input at exactly the configured crop dimensions and return raw `[1, 4+classes, anchors]` or `[1, anchors, 4+classes]` output. Confidence/IoU filtering and class-aware NMS run in Rust, then the existing FOV and prior-target selection runs. Crop/model resolution mismatch is reported instead of resizing. The Precision selector is saved as a preference; the selected artifact determines actual precision. The desktop UI has no Data or export section.

Object Detection and ONNX Runtime/OpenVINO/TensorRT are unavailable for use. Their retained model/Compute controls are disabled for profiles saved with Object Detection; select Pixel Seek to apply a usable profile.

The UDP receiver defaults to port `4200`; the backend suite verifies that changing the port moves the listener and that a subsequent frame is processed. Crop Resolution is configured in the browser settings and sent to the OBS plugin; for example, `256` makes the plugin send a centered 256 × 256 region. The receiver processes each frame exactly as received (no second crop, never resized) and shows it in Preview. Source runtime failures retry every three seconds. If another process owns a requested port, SysX keeps the current listener active and retries the bind; runtime status clears the bind error and updates when the port becomes available. Model controls are shown only in Object Detection mode. The preview HUD shows processing FPS; Preview itself is designed to draw every input frame.

The Rust sidecar owns UDP reassembly, JPEG decoding, processing of the centered crop supplied by the OBS sender, Pixel Seek, bounded latest-frame processing, JSONL storage, local web configuration, and authenticated preview transport. The release executable embeds the sidecar and config assets and extracts a per-process runtime under app data; the Windows build emits `SysX.exe` without an installer. The sidecar processed the 192 × 192 JPEG fixture once on UDP `4202` in an isolated service smoke run; this was not a native-window, performance, Windows, OBS, or hardware validation. Earlier 1280 × 720 synthetic rates were measured by the retired Python implementation and do not measure Rust. No GitHub Actions build workflow is configured. Windows runtime and target-hardware performance remain unverified. No user model is present.

## Requirements

- Windows 10/11 x64 for development, testing, building, and running the portable executable.
- Node.js 20+, pnpm, Rust stable, and Trunk. Node and pnpm build the config assets; application runtime and logic are Rust.
- Windows builds must be produced and validated on Windows (or a Windows CI runner).
- A Windows release is built with [`scripts/build-windows.ps1`](scripts/build-windows.ps1) (no Node needed) and yields `src-tauri/target/release/SysX.exe`. `pnpm build:desktop` remains a development build path and leaves Cargo's native output as `receiver.exe`; use the PowerShell script for the named portable release. Microsoft Edge (preinstalled on Windows 10/11) hosts the receiver window; the default browser is used if Edge is missing. Selected inference runtimes remain machine prerequisites.

```sh
cargo run --manifest-path rust-backend/Cargo.toml -- udp-listen --host 127.0.0.1 --port 4200 --count 1
cargo run --manifest-path rust-backend/Cargo.toml -- udp-send-image src/assets/red-cube-192.jpg --host 127.0.0.1 --port 4200
```

This utility verifies the frame protocol; the production sender is the OBS plugin in `obs-plugin/sysx-canvas-sender`.

## Product constraints

- The UI is English, dark, minimal, and technical.
- The native window is a live monitor; configuration opens in a separate local browser page with Main, Motion, Auto, Recoil, and Settings cards on one scrolling page. The active profile is shown in both pages and the Receiver follows profile changes live.
- Pixel Seek and Object Detection are the only detection strategies.
- User models are loaded only when selected; no model is downloaded automatically.
- Motion Pixel Seek selects exactly one code-profile color (Yellow, Red, or Purple). Auto reuses that selected HSV profile and has no color selector; blue identifies its FOV overlay only.
- Pixel Seek code profiles can restrict detection to a normalized source-frame region; with no region configured, detection uses the full frame.
- FPS, latency, detections, and frame-drop counts are always measured values. Prototype sample data is never used in production.
- The target of 180–360+ processing FPS is a requirement to benchmark, not a performance claim.
- Device I/O supports Medius only through the official `medius 3.4.3` Rust SDK. Discovery, version handshake, fixed 6,000,000 baud, connection health and physical button events belong to the library. The adapter in `src-tauri/src/medius_device.rs` calls `move_rel` and `press/release(Button::LEFT)`; queue records are internal work items, not Native wire frames. Ferrum and MAKCU integrations are removed. Windows/device validation remains pending.
- API implementation notes: [MediusAPI.md](MediusAPI.md). It summarizes SysX device connection, button telemetry, and relative-movement paths and index the broader vendor API families; consult the linked vendor pages for exact signatures and version support.
- Device output uses the verified Medius SDK connection and the existing held-trigger gate, fresh-delta aggregation, 100 ms stale-target cutoff and ±32 per-axis clamp. Auto Delay/Cooldown/Sleep remain configured milliseconds. See [MediusAPI.md](MediusAPI.md); library call completion does not acknowledge a USB/game event.
- Movement settings persist the recoil profile; reconstructed active-state and timed-click branches remain out of the product because their source producers are unavailable. Auto's separate target-valid state machine uses its persisted Delay, Cooldown, and Sleep values and sends a left-click through the verified device path when its trigger is held.
- The historical synthetic benchmark figures above predate the Rust migration. There is no current Rust end-to-end benchmark result.

## Sample frame

This 192 × 192 JPEG is the sample used by the UDP smoke test:

![192 by 192 red cube JPEG sender frame](src/assets/red-cube-192.jpg)

Motion Pixel Seek offers one target color at a time (yellow, red, or purple); Auto reuses the selected Motion HSV profile. The monitor uses blue for the Auto FOV ring while its trigger is held. Motion and Auto use the same shared HSV lookup tables in `rust-backend/src/pixel_seek.rs`: red H 0–10/S 50–255/V 180–255, yellow H 20–40/S 157–255/V 252–255, and purple H 140–160/S 60–255/V 240–255. The UDP receiver decodes JPEG frames to RGB before thresholding; hue uses 0–179, while saturation and value use 0–255.

The Rust sidecar has adapters for ONNX Runtime CPU, OpenVINO, and optional TensorRT. Runtime adapters compile and the decoder/selection behavior has unit coverage; the repository contains no model, so model inference, accelerator availability, Windows packaging, and device behavior remain unverified. CapkfaPlus reconstruction logic was translated selectively; see the development status for the mapped behaviors and limits.

The receiver window is the web monitor in an Edge app window; `index.html` carries a static `NO FRAME` fallback that is visible until the WASM UI mounts. The settings page remains a separate browser page served only on loopback.

Release hardening and the two-stage VMProtect workflow are documented in [`docs/RELEASE_SECURITY.md`](docs/RELEASE_SECURITY.md). A protected release must protect the extracted backend before embedding it into the final one-file `SysX.exe`; protecting only the outer host does not protect the backend while it is running. Windows release packaging fails if the backend or UI bundle is absent, and final packaging requires the post-VMProtect host plus `-VmProtected` unless `-AllowUnprotected` is explicitly used for a local smoke package. Release builds strip debug information and symbols, strip Wasm name/debug metadata before embedding the UI, enable Windows CFG/ASLR/NX and image-load/extension-point mitigations, enable release-only Win32/native debugger guards, and verify the extracted backend against its embedded SHA-256 while running. No authentication secret or reusable credential is stored in the client.

The Rust backend keeps UDP packet reassembly in `rust-backend/src/udp.rs`, decoded input in `receiver.rs`, crop geometry in `crop.rs`, and local configuration in `web_config.rs`. Its movement ticker and the native host aggregate fresh deltas, retain physical-trigger gating and discard targets older than 100 ms; the native host adds sampled recoil and clamps each axis to ±32. Only Medius receives output: internal queue records are retained until a worker invokes `medius_device.rs` through the official Rust SDK on a cloned `Device`. SDK I/O timeouts apply, and library call completion does not acknowledge a game event. Windows/device validation remains pending.
