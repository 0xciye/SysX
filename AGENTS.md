# Project instructions

## Current source status

The active SysX source is Rust (`rust-backend`, `rust-ui`, and `src-tauri`). The retired Python/React implementation is not part of the runtime. The receiver window is the Rust WASM monitor page `/monitor.html`, opened by the native host as a chromeless Edge app window (`msedge --app`, own profile under `%LOCALAPPDATA%\SysX\monitor-window`, default browser fallback); the former `eframe/egui` window is removed and must not be reintroduced. The loopback configuration page (`/config.html`) mounts the same WASM bundle in the browser and persists `app-settings.json`. Do not use older Receiver bundles or stale sidecars for validation.

- The product name is **SysX**. Use SysX in user-facing UI, window metadata, and current product documentation. Preserve internal identifiers and settings storage keys unless migration is explicitly required.

## Product direction

- Build a portable Windows desktop application distributed as one `.exe`, not an installer or browser-hosted website. The executable embeds the Rust backend and configuration assets, extracts the runtime files under app data at launch, opens the local config page, then cleans the extracted runtime on shutdown.
- Keep the English UI dark, minimal, and technically professional.
- Receiver visual system: simple single-page dark Preview surface with near-black blue background, a large feed, compact in-feed HUD plate, operational green for healthy/live state, amber for waiting, red for errors, and monospace only for measured data. Keep navigation out of the monitor page; Web Config remains a separate browser page. Preserve high-contrast text and restrained motion; the persisted source of truth is `design-system/sysx-native-receiver/MASTER.md` and the `.monitor` block in `rust-ui/style.css`. The user allows any UI technology as long as the result is compact, readable, attractive, and complete — but not native egui.
- Keep the receiver monitor focused on Preview, device/connection status, and five-button Mouse State. Launch configuration in a separate browser window at a loopback-only local address when SysX starts; persist settings under app data and restore them on launch. The host exits 3 s after the last `role=monitor` WebSocket closes (60 s if none ever connects). Only one SysX runs per Windows session (named mutex `Local\SysX.Receiver.SingleInstance` in `src-tauri/src/single_instance.rs`); a second launch focuses the existing monitor window (Edge app window titled exactly "SysX") or reopens it from `%LOCALAPPDATA%\SysX\instance.json`, then exits without starting a backend. The backend exits when its `role=host` connection closes, so a killed host never leaves an orphan holding UDP 4200.
- Render the five Mouse State buttons at equal width so Left, Right, Middle, M4, and M5 read as one aligned group.
- Keep the Preview viewport square and cap it at 640 × 640 CSS pixels. Smooth scaling should enlarge small sender frames while preserving aspect ratio; Pixel Perfect should use nearest-neighbor interpolation.
- Keep a circle-only FOV overlay always enabled; let the user set it from 1–360° in the local configuration page. Scale its diameter against the shorter side of the displayed image, so the same degree setting has the same proportion at every sender resolution and 360° stays inside the image/preview. Do not add an enable/disable control.
- Let the local configuration page scroll as additional options are added. The desktop Preview is always visible and its HUD shows only processing resolution, FPS, and latency.
- Keep all local web configuration groups on one vertically scrolling page; do not split settings across tabs or separate pages.
- Show signed X/Y target offsets in crop-pixel units with a compact 2D indicator: the center cross is the selected target and the white marker is the configured destination relative to it. Persist/apply offsets with the global settings action.
- Provide a persisted Trigger button setting in the local web config with exactly Right, Middle, M4, and M5 choices; Left is not allowed. Movement runs only while the selected physical button is held.
- Provide one global **Apply Changes** action that persists the current user-editable settings and restores them on the next launch. Backend selects the model artifact and Compute configures supported runtimes. Precision remains a saved preference because the imported artifact determines its precision.
- Store user-editable settings in `app-settings.json` under app data. The local config page loads that file and writes it on Apply Changes; the backend loads it at startup and creates it with defaults on first launch.
- Keep movement limited to fresh target deltas, the selected held-trigger gate, recoil added to Y, and the verified Medius/Ferrum relative-move APIs. Do not expose or run reconstructed active-state, mode-predicate, direct-offset, or timed-click branches without their source state producers and algorithms.
- Show “Changes applied successfully.” when Apply Changes succeeds, then hide the confirmation after three seconds.
- Keep the Preview empty state visible above its canvas when no frame has arrived; label it “NO FRAME” and show the appropriate startup or sender-waiting status.
- At the 980 × 680 minimum window size, keep Detection Engine labels readable; stack strategy choices at compact widths instead of truncating names. Recapture the native UI after layout changes and do not present older `design-review/` screenshots as current.
- Recapture the monitor after layout changes. Current captures: `design-review/receiver-monitor-web-{live,waiting,narrow}.png`, taken with headless Edge (`--headless=new` + DevTools screenshot) against an isolated `receiver-backend serve` on UDP 4299 and `sysx-sender-selftest` frames — this opens no visible window. Do not launch SysX.exe or any visible window while the user is gaming/using the machine without asking first; older `design-review/` images are historical.
- The monitor Preview canvas (`rust-ui/src/preview.rs`) draws detection boxes, FOV, target line/ring, and the Object Detection `[id] score%` summary (bottom-center, so the HUD plate keeps the top-left), mapping original-frame coordinates by subtracting `crop_x/crop_y`. Device/button state reaches the page via the host's `device_status` command, which the backend validates and republishes as `state.device`. The backend only sends preview frames younger than 1 s, so a reconnecting page never shows a stale frame as "Receiving".
- Do not terminate existing Receiver/backend processes during native smoke checks. A process inspection identified an older orphaned backend as the current owner of UDP port `4200`; leave it untouched. A separate release-mode validation build with isolated app data previously previewed 192 × 192 MJPEG on port `4202`.
- Receiver waits automatically for frames and begins preview on the first valid frame. Never add Start, Pause, or Stop controls.
- Show “Waiting for sender” once the authenticated backend connection is ready; reserve “Starting receiver” for backend startup and show connection/runtime failures as errors.
- Default UDP input port is `4200` across the app, backend, local verifier, and documentation.
- MJPEG from the OBS sender plugin (`obs-plugin/sysx-canvas-sender`) is the only production frame source. The receiver answers each new sender with `SYSCFG 1 CROP <Crop Resolution>`; the plugin crops that centered square on the GPU before encoding, and the receiver still applies its centered crop (identity when sizes match, so full frames from other senders also work) before detection and Preview. Do not add local sample, image, or video source controls to the desktop UI.
- Show model controls (including import) only in Object Detection mode; do not add a Data or export section to the desktop UI.
- Import a single model bundle containing ONNX `.onnx`, TensorRT `.engine`/`.plan`, and OpenVINO IR `.xml` plus `.bin`. Backend selects one artifact. ONNX Runtime uses CPU; OpenVINO supports available CPU/GPU/NPU devices; TensorRT requires a GPU engine and an SDK-enabled build. Keep Precision as a saved preference unless runtime precision selection is implemented.
- Present Pixel Seek and Object Detection as radio cards in Detection Engine; keep them side by side at normal widths and stack them when compact so both names remain readable.
- Present Pixel Seek and Object Detection as separate Detection Engine cards. Show the Yellow/Red/Purple target-color choices in a separate full-width row below the cards when Pixel Seek is selected; hide them in Object Detection.
- Keep the Pixel Seek card free of explanatory copy.
- Render Pixel Seek detections as bounding boxes tinted to the selected target color; do not show AI class/confidence labels for Pixel Seek.
- Object Detection always shows Min confidence as a 0–1 slider, including before a model is selected; do not render detections below it in Preview.
- Object Detection Preview uses stable distinct class colors for boxes and shows a compact `[id] score% | ...` summary; keep the solid center-to-target line and ring.
- Implement only `pixel_seek` and `object_detection` strategies.
- For Rust Object Detection, support raw YOLOv8 output shaped `[1, 4+classes, anchors]` or `[1, anchors, 4+classes]`, use the model's configured confidence/IoU values, and perform class-aware NMS. Do not apply raw-output decoding or NMS to already decoded/NMS-filtered output; reject unsupported output shapes.
- Runtime adapters are implemented, but there is no user model in the repository and no real-model, Windows, TensorRT, OpenVINO-device, or hardware validation. State those limits when reporting support.
- Pixel Seek selects exactly one target color at a time: yellow, red, or purple. HSV thresholds are code-defined in `rust-backend/src/pixel_seek.rs`; the UI must not expose editable HSV ranges. Preserve the established red H 0–10/S 50–255/V 180–255, yellow H 20–40/S 157–255/V 252–255, and purple H 140–160/S 60–255/V 240–255 ranges (OpenCV H range 0–179).
- Crop Resolution is persisted in local web config; `256` means a centered 256 × 256 crop. Reject frames smaller than the configured crop rather than silently clamping or resizing. Pixel Seek ROI is code-defined per `PixelColorRule` as normalized original-frame coordinates `(left, top, right, bottom)`; `None` means the entire frame. Return boxes in original frame coordinates and map them onto cropped Preview using the crop origin.

## Architecture boundaries

- Keep all application and runtime logic in Rust: a native host without a UI toolkit (backend supervision, Medius/Ferrum I/O, movement), the Leptos/WebAssembly monitor + config UI, and the Rust backend sidecar. The Windows release is one self-extracting `SysX.exe`; embed the sidecar and UI assets and extract them into a per-process app-data runtime directory. Do not reintroduce Python or React/TypeScript application sources. Node/pnpm are optional build tooling; `scripts/build-windows.ps1` builds everything without them.
- Build the config UI with Trunk through `scripts/build-rust-ui.mjs`; the native host does not load that bundle, while `web_config.rs` serves it at `/config.html` for the separate loopback browser page.
- Keep frame acquisition, processing, persistence, and rendering decoupled.
- In the Rust runtime, keep packet reassembly in `rust-backend/src/udp.rs`, UDP/JPEG receive in `receiver.rs`, crop geometry in `crop.rs`, model runtimes in `inference.rs`, processing in `pipeline.rs`, movement in `movement.rs`, and local web config in `web_config.rs`. UDP is the only production frame source.
- Keep target selection and mouse output as a post-detection stage. Pixel Seek consumes its mask; Object Detection applies score gates and the reconstructed center-ellipse, nearest-box, prior-box coverage, and class anchor rules. Port reconstructed formulas only where their runtime inputs map to current settings/state; do not fabricate missing class groups, feature flags, or state producers.
- Keep crop-target conversion and short-window delta aggregation in `rust-backend/src/movement.rs`; the Rust service supplies each processed target. The native host's pending-delta merge, freshness check, trigger mapping, and per-command clamp live in `src-tauri/src/movement.rs`; discard any pending delta older than 100 ms before merging it with a new one. Native device monitors own vendor API calls.
- Apply the requested per-axis exponential filter to the selected target coordinate using independently configured X/Y alpha values from 0.01 to 1.0; alpha 1.0 leaves the coordinate unchanged. Preserve raw `target_xy`, publish the filtered coordinate separately, and reset filter history when the target disappears or pipeline configuration changes. Use the filtered coordinate for Preview and device movement.
- Run detection on the whole processed image independently from FOV. Filter only candidates passed into later targeting logic by the centered FOV circle. Pixel Seek masks the whole frame but yields exactly one target per frame: the topmost accepted mask pixel inside the FOV (re-searched every frame), and only the blob containing that pixel is reported/drawn. Other colored regions, including anything outside the FOV, are masked but not reported (user requirement). Target lock (anti-flip, both engines): Pixel Seek keeps the previous target blob for 100 ms and searches only its box grown by max(12 px, 50 % of its larger side) inside the FOV, so higher pixels next to the target are still climbed while another target elsewhere in the FOV is ignored; when nothing remains there it falls back to the topmost FOV pixel. Object Detection keeps its reconstructed prior-box lock (same class, >50 % overlap, switch only if a new box is ~3x closer to center).
- Mouse motion uses the independently smoothed crop target, target offsets, the NCAF controller, a fractional residual accumulator, and the documented Medius `move_rel` or Ferrum `km.move` transport. Backend and native pending queues sum fresh deltas before API output; stale targets expire after 100 ms and each axis is clamped to ±32 device units per command. Conversion uses the sensitivity/DPI formula in `rust-backend/src/movement.rs` (defaults: sens 0.235, DPI 800). Do not add reconstructed mode or timed-click branches without their state producers.
- Apply the supplied NCAF three-zone movement controller, cubic Bézier response, and occasional micro-corrections in `rust-backend/src/movement.rs`; do not expose them as configuration controls or persisted settings. Keep one latest target sample and let an independent short-interval ticker recompute movement while it remains fresh; retain the native host's stale-target and ±32 clamps.
- Keep the type-0 async serial queue consumer in `src-tauri/src/serial_queue.rs` behind a writer interface; retain command bytes until completion. Do not wire it to a device or treat `request_ms` as an end-to-end deadline until a vendor writer and its completion ownership are implemented and validated. Leave nonzero command kinds outside this reconstruction.
- Use bounded queues and discard obsolete frames when processing falls behind.
- Preview must show every input frame (user requirement: preview FPS = input FPS). The backend wakes each preview socket per processed frame through a `tokio::sync::watch` channel (never timer polling: Windows timers tick at ~15.6 ms and capped Preview near 60 FPS), forwards the sender's original JPEG without re-encoding, shares processed frames as `Arc` (no image copies), and `state()` must not block on the UDP source lock (it reads `SourceView`). The page decodes with `createImageBitmap` off the main thread. With a 240 FPS libobs source (headless, 2026-10-15) the monitor page received 230.3 and drew 229.7 frames/s; a raw WebSocket client received 224.8 frames/s. Visible frames are still limited by the monitor's refresh rate. The HUD `ms` is `total_processing_ms`: the per-frame detection time (crop → detect → target choice), excluding network, JPEG decode, and drawing.
- Keep source, inference, and display resolutions distinct. Preview scaling must not alter detection input.
- Keep preview fitting, detection-box mapping, and HiDPI backing-size math in pure helpers in `rust-ui/src/layout.rs` with Rust unit coverage.
- Keep Preview confidence filtering in a pure helper with regression coverage for the threshold boundary, missing confidence, and Pixel Seek bypass.
- Show source/inference resolutions and measured performance/drop counters in the compact Preview HUD; distinguish source, processing, and preview FPS. Source FPS is valid decoded frames observed by the receiver over a trailing one-second window; processing FPS is completed detections over a trailing one-second window. The processing completion-time deque holds 4096 samples and has a regression test above the requested 360 FPS range; update its capacity and test together if the supported rate rises beyond that window's capacity.
- Show the device reported by the inference runtime, not only the configured device preference.
- Keep browser configuration controls keyboard-visible and provide at least 24 CSS px pointer targets for compact switches; configuration controls must remain keyboard accessible.
- Apply boxes and labels in display coordinates after scaling the source image.

## Data and safety

- Never fabricate FPS, latency, detections, model metadata, or benchmark results.
- Keep any synthetic Pixel Seek microbenchmark explicitly separate from production color profiles and end-to-end performance claims. No current Rust benchmark is available; historical Python benchmark figures are not Rust performance evidence.
- Retain a backend integration test that changes the UDP port, confirms the new bind, and processes a frame on the new port.
- Use `src/assets/red-cube-192.jpg` as the actual JPEG fixture for sender protocol smoke checks; preserve its SOI/EOI markers.
- Latest macOS 15.3.1 ARM64 synthetic 1280×720 backend run measured 179.95/179.93/180.05 FPS (sender/source/processing) at 180 and 359.99/359.81/359.79 FPS at 360, with zero drops; this does not validate Windows or the OBS sender.
- After adding SOI/EOI validation during UDP reassembly, 3-second 1280×720 synthetic runs measured 179.88/179.96/179.87 sender/source/processing FPS at the 180 target and 359.96/360.06/359.79 at the 360 target, with 0 skipped sender slots, input drops, transport drops, invalid packets, or rejected frames and 181 preview messages per run. This remains backend-only synthetic evidence.
- A current packaged macOS UI smoke snapshot with the 192×192 sample at a 180 FPS send target showed 180.0 source, 179.5 processing, and 60.1 preview FPS, 5 input drops, and 0 transport drops. This is loopback test evidence, not OBS or Windows validation.
- A macOS 15.3.1 ARM64 release-mode Tauri validation app with isolated app data received the 192×192 JPEG fixture on UDP `4202` during an 8-second 360-FPS-target run. The sender measured 350.74 FPS with 74 skipped slots; a live HUD snapshot showed 355.0 source and processing FPS, 60.0 preview FPS, 0 input/transport drops, and 0.04 ms processing latency. This is local synthetic-sender evidence, not OBS, Windows, sustained 360-FPS sender, or target-hardware validation.
- Include requested sender FPS, measured source FPS, processing FPS, preview FPS, and available sender/receiver drops in benchmark reports.
- Measure the live Tauri preview separately from synthetic backend runs; report the OS, input fixture, requested/measured rates, and available drop counters for each.
- Never download or substitute a model for the user's own model.
- Validate every network packet, dimensions, chunk count, payload length, and aggregate memory before allocating or decoding. Check JPEG SOI on chunk 0 and EOI on the final chunk before retaining those payloads; discard any partial assembly if a boundary marker is invalid. UDP image payloads must be complete JPEG frames; do not accept PNG or other formats through the production sender path.
- Preserve AI class IDs exactly. Pixel Seek confidence is null unless a probabilistic metric is separately implemented.
- Do not silently resize UDP frames for Object Detection. Report and count model-resolution mismatches.
- Removing a registry model must preserve its imported model bundle files. Fall back to Pixel Seek only when the active model is removed.
- Persist data without blocking frame processing; report storage failures.
- Exporting session CSV must flush queued JSONL records first and keep file I/O off the asyncio event loop.

- Add automated tests for new parsing, processing, persistence, and coordinate-mapping behavior. The user explicitly requested automated tests in the source specification.
- Do not say a Windows build or hardware throughput target passed unless it was actually run on Windows or the target hardware.

This does not validate the native window, Windows, OBS, performance targets, or hardware. App shutdown must stop the backend process and remove its extracted runtime directory.
- A current native 980 × 680 review confirmed stacked Detection Engine choices and a scrollable Settings panel; the `design-review/` screenshots remain historical and must not be presented as that review.

Windows validation scripts remain available for manual execution; they verify UDP `4200` and 192×192 frame reassembly, then launch the standalone `SysX.exe`, confirm its embedded backend binds UDP `4200`, and check normal shutdown. They do not verify visual rendering.
- In Windows PowerShell build scripts, check `$LASTEXITCODE` after every native command. `$ErrorActionPreference = "Stop"` alone does not reliably turn native nonzero exit codes into terminating errors.
- Use `pnpm native:dev` for the native monitor and `pnpm build:desktop` for the portable executable; do not add Tauri CLI dependencies or WebView runtime assumptions.
- Validate the selected Compute target through the selected runtime before inference and surface recovery guidance for unavailable devices.
- Update `README.md`, `AGENTS.md`, and `DEVELOPMENT.md` at each completed project milestone, as requested.
- Use the approved tokens in `design-system/MASTER.md` for all production UI work.
- Use `public/receiver-mark.svg` as the canonical SysX mark; keep desktop bundle icons visually aligned with this SVG.
- Device status in the desktop header checks Medius by its official CH343 VID/PID and version handshake, and Ferrum through a valid `km.version()` reply. Medius uses the official crate's fixed 6,000,000 baud setting; Ferrum Legacy CP210x uses its documented 115,200 baud. Do not substitute Makcu baud values. Movement uses the verified Medius connection or detected Ferrum Legacy CP210x connection while the configured physical trigger is held. Hardware movement and button telemetry still require Windows/device validation.

## Backend notes

- Backend modules and regression tests live in `rust-backend/src` and the Rust crate tests. Do not restore the removed Python backend.
- UDP v1 uses the bounded `RCVR` chunk protocol in `rust-backend/src/udp.rs`. Keep each datagram at or below 1200 bytes, validate metadata before retaining payloads, cap frame/reassembly memory, expire incomplete frames during socket-idle timeouts as well as while packets arrive, and preserve latest-frame semantics.
- Retry frame-source runtime errors every 3 seconds. Keep the current listener active while a requested replacement port is unavailable; once it binds, update runtime state and clear the recovered error.
- Rust `LatestFramePipeline` must stay bounded and discard a result if strategy configuration changed while it was processing.
- Detection persistence runs outside the processing worker. Surface storage failures; never claim dropped records were saved.
- The Rust `udp-send-image` and `udp-listen` CLI commands are local protocol verifiers, not a production sender or a substitute for desktop integration.
- The OBS plugin follows `docs/OBS_RECEIVER_PROTOCOL.md`; keep that document, `rust-backend/src/udp.rs`, `rust-backend/src/receiver.rs` (SYSCFG), and `obs-plugin/sysx-canvas-sender` aligned. Configuration is compile-time only (user request): `kReceiverHost`/`kReceiverPort` and the other `k*` constants at the top of `sysx_canvas_sender.cpp` (default 127.0.0.1:4200); do not add an ini/settings file. Keep the DLL dependency-free: libjpeg-turbo and the VC++ runtime are linked statically (static CRT) so it imports only Windows system DLLs, and libobs functions are resolved from the loaded `obs.dll`. Verify changes headlessly with `sysx-sender-selftest` and `sysx-obs-host-check` (real OBS 32.2.2 `obs.dll`, D3D11, no window) against `receiver-backend udp-listen`; HDR canvases are skipped silently, and loopback delivery kept up with 240/360 FPS render rates (234.2/356.8 FPS). The OBS Studio UI and LAN delivery between two computers are still unvalidated. The plugin must write nothing to the OBS log (user request); do not add `blog` calls.
- Add Rust coverage for new parsing, processing, persistence, and coordinate-mapping behavior in the corresponding Rust crate.
