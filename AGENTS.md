# Project instructions

> **Current availability:** Pixel Seek is the only usable detection engine. Object Detection and its ONNX Runtime, OpenVINO and TensorRT integrations are **not ready for use**. Their source/dependencies remain for development; build and unit-test results are not functional validation. SysX supports **Medius only** through its Rust SDK.

## Current source status

The active SysX source is Rust (`rust-backend`, `rust-ui`, and `src-tauri`). The retired Python/React implementation is not part of the runtime. The receiver window is the Rust WASM monitor page `/monitor.html`, hosted in the native Wry/WebView2 window when available, with a chromeless Edge app fallback (`msedge --app`, own profile under `%LOCALAPPDATA%\SysX\monitor-window`, default browser as a final fallback); the former `eframe/egui` window is removed and must not be reintroduced. The loopback configuration page (`/config.html`) mounts the same WASM bundle in the browser and persists `app-settings.json`. Do not use older Receiver bundles or stale sidecars for validation.

- The product name is **SysX**. Use SysX in user-facing UI, window metadata, and current product documentation. Preserve internal identifiers and settings storage keys unless migration is explicitly required.

## Architecture boundaries

- Keep all application and runtime logic in Rust: a native host (backend supervision, Medius I/O, movement and the Wry/WebView2 monitor shell), the Leptos/WebAssembly monitor + config UI, and the Rust backend sidecar. The Windows release is one self-extracting `SysX.exe`; embed the sidecar and UI assets and extract them into a per-process app-data runtime directory. Do not reintroduce Python or React/TypeScript application sources. Node/pnpm are optional build tooling; `scripts/build-windows.ps1` builds everything without them.
- Build the config UI with Trunk through `scripts/build-rust-ui.mjs`; the native host does not load that bundle, while `web_config.rs` serves it at `/config.html` for the separate loopback browser page.
- Keep frame acquisition, processing, persistence, and rendering decoupled.
- In the Rust runtime, keep packet reassembly in `rust-backend/src/udp.rs`, UDP/JPEG receive in `receiver.rs`, crop geometry in `crop.rs`, model runtimes in `inference.rs`, processing in `pipeline.rs`, movement in `movement.rs`, and local web config in `web_config.rs`. UDP is the only production frame source.
- Keep target selection and mouse output as a post-detection stage. Pixel Seek consumes its mask; Object Detection applies score gates and the reconstructed center-ellipse, nearest-box, prior-box coverage, and class anchor rules. Port reconstructed formulas only where their runtime inputs map to current settings/state; do not fabricate missing class groups, feature flags, or state producers.
- Keep the Auto feature isolated in `src-tauri/src/auto.rs`; its explicit left-click timing state remains separate from `movement.rs` and is fed by the backend's center-crossing `auto_target_valid` event.
- Keep Auto timing values in milliseconds. A center crossing arms one delayed click; once Delay starts, target loss does not cancel it and additional crossings do not restart it or queue more clicks. Trigger release, disabling Auto, or changing its timing cancels a pending click. After a click, target loss rearms the cycle. Cooldown starts when the click command is emitted and survives target loss, trigger rearming, and control changes; Sleep only spaces Auto polling without extending the firing interval. Auto configuration controls reach the host independently of frames, invalidate old targets, and increment a revision that cancels pending clicks even across rapid disable/re-enable or trigger changes.

- Keep crop-target conversion and short-window delta aggregation in `rust-backend/src/movement.rs`; the Rust service supplies each processed target. The native host's pending-delta merge, freshness check, trigger mapping, and per-command clamp live in `src-tauri/src/movement.rs`; discard any pending delta older than 100 ms before merging it with a new one. Native device monitors own vendor API calls.
- Apply the requested per-axis exponential filter to the selected target coordinate. Smoothing is a strength from 1 to 50 per axis with a Min and a Max (user request): each new track (after target loss or a pipeline reconfiguration) draws a strength uniformly in [Min, Max] per axis and keeps it for the track; alpha = 1/strength, so 1 leaves the coordinate unchanged. Older files' `smoothingAlphaX/Y` migrate to min = max = 1/alpha (clamped). Movement does not use the image-smoothed coordinate: the controller smooths the raw target error around a constant-velocity prediction carried by the target's own velocity and, once calibrated, by the image shift of the moves applied between captures, so smoothing filters only deviations of the target's own motion and never delays the aim's own motion (image smoothing made the aim overshoot: 14/27/55 px at strength 10/20/50). Preview still shows `smoothed_target_xy`. The velocity filter is deliberately not slowed by the strength (that made the aim trail and overshoot more). Simulation (saved calibration, 240 FPS): at every strength 1–50 a still target 63 px away is reached in 0.19 s with ≤ 4 px overshoot; strafing error 11 px at 1, 12–13 px at 10–35, 15 px at 50.
- Run detection on the whole processed image independently from FOV. Filter only candidates passed into later targeting logic by the centered FOV circle. Pixel Seek masks the whole frame but yields exactly one target per frame: the topmost accepted mask pixel inside the FOV (re-searched every frame), and only the blob containing that pixel is reported/drawn. Other colored regions, including anything outside the FOV, are masked but not reported (user requirement). Target lock (anti-flip, both engines): Pixel Seek keeps the previous target blob for 100 ms and searches only its box grown by max(12 px, 50 % of its larger side) inside the FOV, so higher pixels next to the target are still climbed while another target elsewhere in the FOV is ignored; when nothing remains there it falls back to the topmost FOV pixel. Object Detection keeps its reconstructed prior-box lock (same class, >50 % overlap, switch only if a new box is ~3x closer to center).
- Mouse motion uses the independently smoothed crop target, target offsets, the NCAF controller, a fractional residual accumulator, and the documented Medius Rust SDK `move_rel` transport. Backend and native pending queues sum fresh deltas before API output; stale targets expire after 100 ms and each axis is clamped to ±32 device units per command. Counts follow the game, not a formula: one injected count turns the camera yaw × sens degrees (DPI only describes the physical mouse and plays no part), and image pixels per count also depend on FOV and capture resolution, so the backend measures px/count. Calibrated, the correction closes the estimated error in image px/s (time constant 35 ms, ×(1 + 4 × relative error) while the estimate is rough; floor 300 px/s ÷ the same factor; cap 4000 px/s; NCAF and the per-stroke speed curve shape it) and converts with the measured px/count; feedforward is likewise divided by that caution factor. Before the first estimate (~0.1 s; never with a saved file) a deliberately slow step of 0.0035/sens counts per px runs (default sens 0.25; there is no DPI setting — DPI only describes the physical mouse; older settings files with `dpi` still load and drop it on the next save). The dead zone is at least 0.6/1.2 counts, so coarse counts do not hunt; after calibration the probe is sized to ~0.8 px (1–2 counts) and is off where one count exceeds 3 px. Do not add reconstructed mode or timed-click branches without their state producers.
- Movement controller in `rust-backend/src/movement.rs`: NCAF three-zone controller with velocity prediction, then per-stroke variation: each stroke (acquire → settle) draws once a heading curve that fades as the gap closes, an acceleration ramp, a deceleration strength (NCAF near-zone exponent) and the Bézier speed-response control points; the Bézier shapes the step length, not each axis. Time-correlated Ornstein-Uhlenbeck drift (lateral offset along the perpendicular and a speed scale) replaces the independent ±1 micro-corrections; curve and drift fade to zero near the target. No forced ±1 step: outside a 2 px stop / 4 px resume dead zone (hysteresis) a minimum vector step of ~0.4 count/tick accumulates in the residual, so small diagonal errors walk diagonally; settling clears residual, stroke and drift; a residual is dropped only when its axis reverses. Do not expose any of it as configuration controls or persisted settings; tests seed the RNG. Target tracking (on top of the controller above): fast tracking starts within ~0.1 s at the intended 240 FPS and learns while it runs. While the trigger is held the backend calibrates online — a random ±2-count probe (every tick until calibrated, 20% after) is independent of detection noise, the latency (0–100 ms in 4 ms steps) is the one where the probe best explains the change in apparent target rate over 8 ms spans (2 frames at 240 FPS; one frame interval of slack keeps lower rates working), and px/count is the instrumental-variable slope over all applied moves (forgetting 0.999; samples only while the trigger is held). It switches on at ≤40% relative standard error (≤15% when the probe moves the image under 0.3 px, i.e. below whole-pixel detection) using px/count raised by 1.5 standard errors (too high only slows tracking; too low makes the loop oscillate, so no guessed default is used — before the first estimate the original uncompensated path runs), follows estimates up to 60%, and is dropped only after ~3 s of new evidence disagrees. Calibrations at ≤15% error are saved per sensitivity to `motion-calibration.json` in app data (background write, at most every 2 s, 16 entries, invalid entries ignored) and loaded at start and on a sensitivity change, so later sessions track from the first frame; a loaded value is kept until ~3 s of new evidence exists, while a freshly learned rough value follows every new estimate (so an early wrong latency is corrected). Once calibrated: target velocity is measured per new frame with the camera motion of applied moves added back; each tick uses the error estimated for now (frame error + target velocity × time since the scene was captured − px/count × moves applied since then) so moves are not re-sent for a stale frame; 0.9 × velocity feedforward; a speed-scaled near-zone NCAF lift (up to 60% toward 1 at 600 px/s); no settling while the target moves ≥40 px/s. Only a new acquisition (target lost or a >48 px jump) gets the start-up ramp. Backend learns the trigger state from the host's `device_status`. Simulation only (`startup_report`, `simulation_report`, `calibration_timing_report` ignored tests) — not game or hardware evidence: at 240 FPS fast tracking is on after 0.06–0.09 s median (0.25–12 px/count), 0.15 s with 50 ms latency, 0.12 s at 60 FPS, stable in every case; with a saved file it is on from the first frame (first-second error about 70–80% of a fresh start); at 0.05 px/count (sub-pixel probe) the estimate is rough and on average no better than uncompensated. Keep one latest target sample and let an independent short-interval ticker recompute movement while it remains fresh; retain the native host's stale-target and ±32 clamps.
- Movement output uses the type-0 `SerialCommandQueue` in `src-tauri/src/serial_queue.rs`. A `ThreadedSerialWriter` invokes the Medius Rust SDK adapter on a cloned `Device`, keeping button telemetry independent of writes. `[M, dx_le, dy_le]` and `[C]` are internal work records, never device wire frames. Take targets only when the queue is idle; retain bytes until completion and preserve fresh-delta aggregation. SDK-managed I/O timeouts apply; `request_ms` is a forwarded writer hint, not a queue-enforced cancellation deadline or device acknowledgement.
- Use bounded queues and discard obsolete frames when processing falls behind.
- Preview must show every input frame (user requirement: preview FPS = input FPS). The backend wakes each preview socket per processed frame through a `tokio::sync::watch` channel (never timer polling: Windows timers tick at ~15.6 ms and capped Preview near 60 FPS), forwards the sender's original JPEG without re-encoding, shares processed frames as `Arc` (no image copies), and `state()` must not block on the UDP source lock (it reads `SourceView`). The page decodes with `createImageBitmap` off the main thread. With a 240 FPS libobs source (headless, 2026-10-15) the monitor page received 230.3 and drew 229.7 frames/s; a raw WebSocket client received 224.8 frames/s. Visible frames are still limited by the monitor's refresh rate. The HUD `ms` is `total_processing_ms`: the per-frame detection time (crop → detect → target choice), excluding network, JPEG decode, and drawing.
- Keep source, inference, and display resolutions distinct. Preview scaling must not alter detection input.
- Keep preview fitting, detection-box mapping, and HiDPI backing-size math in pure helpers in `rust-ui/src/layout.rs` with Rust unit coverage.
- Keep Preview confidence filtering in a pure helper with regression coverage for the threshold boundary, missing confidence, and Pixel Seek bypass.
- HUD FPS and latency numbers are colored green/amber/red (user-specified) via the tested pure helpers in `rust-ui/src/layout.rs`: `fps_tone` compares processing FPS with the measured input (source) FPS (≥ 80 % green, ≥ 50 % amber, below red); `latency_tone` uses a fixed 0–10 ms scale for every input rate (< 4 ms green, < 7 ms amber, ≥ 7 ms red), and above `LATENCY_HIGH_MS` (10 ms) the HUD adds a red "(HIGH)" tag. No color without measurements.
- The HUD FPS is processing FPS (user-confirmed). Preview FPS is a goal, not a HUD readout: Preview must keep up with the input FPS; no preview-FPS counter is computed in the page. Source FPS is valid decoded frames observed by the receiver over a trailing one-second window; processing FPS is completed detections over a trailing one-second window. The processing completion-time deque holds 4096 samples and has a regression test above the requested 360 FPS range; update its capacity and test together if the supported rate rises beyond that window's capacity.
- The config page only edits and saves settings (user request): the backend sends preview frames to `role=monitor` sockets only, never to the config page or the host, so it shows no runtime readouts such as the actual inference device. The monitor draws each frame once: detections/target are updated untracked so only the `frame` signal wakes the redraw, 100 ms state updates only notify when a value changed, one `createImageBitmap` decode runs at a time (newer frames mark the canvas dirty and the newest is drawn next), and the canvas backing store is resized only when its size changes.
- Keep browser configuration controls keyboard-visible and provide at least 24 CSS px pointer targets for compact switches; configuration controls must remain keyboard accessible.
- Apply boxes and labels in display coordinates after scaling the source image.

## Data and safety

- Never fabricate FPS, latency, detections, model metadata, or benchmark results.
- Keep any synthetic Pixel Seek microbenchmark explicitly separate from production color profiles and end-to-end performance claims. No current Rust benchmark is available; historical Python benchmark figures are not Rust performance evidence.
- Retain a backend integration test that changes the UDP port, confirms the new bind, and processes a frame on the new port.
- Use `src/assets/red-cube-192.jpg` as the actual JPEG fixture for sender protocol smoke checks; preserve its SOI/EOI markers.
- After adding SOI/EOI validation during UDP reassembly, 3-second 1280×720 synthetic runs measured 179.88/179.96/179.87 sender/source/processing FPS at the 180 target and 359.96/360.06/359.79 at the 360 target, with 0 skipped sender slots, input drops, transport drops, invalid packets, or rejected frames and 181 preview messages per run. This remains backend-only synthetic evidence.
- Include requested sender FPS, measured source FPS, processing FPS, preview FPS, and available sender/receiver drops in benchmark reports.
- Measure the live Tauri preview separately from synthetic backend runs; report the OS, input fixture, requested/measured rates, and available drop counters for each.
- Never download or substitute a model for the user's own model.
- Validate every network packet, dimensions, chunk count, payload length, and aggregate memory before allocating or decoding. Check JPEG SOI on chunk 0 and EOI on the final chunk before retaining those payloads; discard any partial assembly if a boundary marker is invalid. UDP image payloads must be complete JPEG frames; do not accept PNG or other formats through the production sender path.
- Preserve AI class IDs exactly. Pixel Seek confidence is null unless a probabilistic metric is separately implemented.
- Do not silently resize UDP frames for Object Detection. Report and count model-resolution mismatches.
- Removing a registry model must preserve its imported model bundle files. Fall back to Pixel Seek only when the active model is removed.
- Persist data without blocking frame processing; report storage failures.

### Release hardening

- Keep release hardening separate from vision, targeting, movement, and queue logic. The release profiles strip symbols/debug information and use LTO; Windows also enables Control Flow Guard; debug/test builds must remain debuggable.
- The Windows release-only debugger guard lives in `rust-backend/src/security.rs` and `src-tauri/src/security.rs`. Do not add debugger checks to debug/test builds or alter runtime behavior in those builds.
- Keep the Windows release packaging fail-fast: `src-tauri/build.rs` must reject a missing backend sidecar or missing Trunk bundle instead of producing a non-runnable host.
- `src-tauri/build.rs` embeds the backend and UI into one host executable. When VMProtect is used, protect the backend before embedding it, then protect the final `SysX.exe`; protecting only the outer host leaves the extracted backend exposed at runtime. Follow `docs/RELEASE_SECURITY.md` and use `scripts/prepare-vmprotect.ps1`.
- The release host verifies the final backend and all immutable UI files against a build-time SHA-256/length manifest before launching any runtime code. Keep this enforcement off for debug/test launches, including release-profile tests. User settings/calibration/models/session data stay outside the immutable runtime.
