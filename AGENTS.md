# Project instructions

> **Current availability:** Pixel Seek is the only usable detection engine. Object Detection and its ONNX Runtime, OpenVINO and TensorRT integrations are **not ready for use**. Their source/dependencies remain for development; build and unit-test results are not functional validation. SysX supports **Medius only** through its Rust SDK.

## Current source status

The active SysX source is Rust (`rust-backend`, `rust-ui`, and `src-tauri`). The receiver is a native Slint desktop window in `src-tauri/src/monitor_window.rs`, with bounded authenticated IPC/JPEG workers in `native_monitor.rs`. Preserve the existing monitor design; do not introduce Win32/GDI controls, egui, WebView2/Wry or a browser fallback. The separate Leptos/WASM `/config.html` page only edits settings. `/monitor.html` returns 404. Never render a preview or preview-shaped boot fallback in web config.

- The product name is **SysX**. Use SysX in user-facing UI, window metadata, and current product documentation. Preserve internal identifiers and settings storage keys unless migration is explicitly required.

## Product direction

- Build a portable Windows desktop application distributed as one `.exe`, not an installer or browser-hosted website. The executable embeds the Rust backend and configuration assets, extracts the runtime files under app data at launch, opens the local config page, then cleans the extracted runtime on shutdown.
- Keep the English UI dark, minimal, and technically professional.
- Receiver visual system: simple single-page dark Preview surface with near-black blue background, a large feed, compact in-feed HUD plate, operational green for healthy/live state, amber for waiting, red for errors, and monospace only for measured data. Keep navigation out of the monitor page; Web Config remains a separate browser page. Preserve high-contrast text and restrained motion; the persisted source of truth is `design-system/sysx-native-receiver/MASTER.md` and the Slint component in `src-tauri/src/monitor_window.rs`. The user allows any UI technology as long as the result is compact, readable, attractive, and complete — with the native Slint renderer; do not retheme it.
- Keep the native receiver focused on Preview, device/connection status, active profile and five-button Mouse State. Configuration opens separately in a loopback browser page. Closing the monitor hides it and closes its preview connection; a config client keeps the backend alive, otherwise exit after a 3 s grace period. A second launch focuses the native window or signals `Local\SysX.NativeMonitor.Show` to reopen it. The backend exits when the owned host connection closes. No browser fallback belongs in the receiver lifecycle.
- Color Filter (persisted `colorFilter`, per profile; toggle in the Main card's Modules group below Motion, Auto and Recoil; `set_color_filter` command): when on, the pipeline blacks out every pixel outside the selected Pixel Seek color profile *before* Motion, Auto (and Object Detection) process the frame (`pixel_seek::color_filtered`), so both see only the selected color. Preview shows that same filtered image without re-encoding: the frame message carries the applied mask packed one bit per pixel (pixel `i` = bit `i % 8` of byte `i / 8`, `color_mask` metadata) between the metadata and the original JPEG, and the native decode thread blacks out the unset pixels. Toggling reconfigures the pipeline. Because the filter uses the same profile as Pixel Seek, its targets are unchanged; the filter adds one mask and image-copy pass to processing time.
- Render the five Mouse State buttons at equal width so Left, Right, Middle, M4, and M5 read as one aligned group.
- Keep the Preview viewport square and cap it at 640 × 640 CSS pixels. Smooth scaling should enlarge small sender frames while preserving aspect ratio; Pixel Perfect should use nearest-neighbor interpolation.
- Keep a circle-only FOV overlay always enabled; let the user set it from 1–360° in the local configuration page. Map degrees to pixels against a fixed 640 px reference (`FOV_REFERENCE_PX` in `targeting.rs` and `rust-ui/src/layout.rs`: 360° = 640 source px, limited to the image), not the crop side: the crop is a native-resolution cutout, so the same degree setting is the same circle on screen at every Crop Resolution (user request). Do not add an enable/disable control.
- Let the local configuration page scroll as additional options are added. The desktop Preview is always visible and its HUD shows only processing resolution, FPS, and latency.
- Treat the configuration page as a responsive rectangle: use a balanced three-column, two-row card grid on wide desktop layouts with Main, Motion, Auto on the first row and Recoil plus Settings on the second. Use two columns at medium widths and one column when compact, preserving readable labels, keyboard focus, and full-size controls.
- Keep all local web configuration groups on one vertically scrolling page; do not split settings across tabs or separate pages.
- Show signed X/Y target offsets in crop-pixel units with a compact 2D indicator: the center cross is the selected target and the white marker is the configured destination relative to it. Persist/apply offsets with the global settings action.
- Provide a persisted Trigger button setting in the local web config with exactly Right, M4, and M5 choices; Left (fires) and Middle (cycles profiles) are not allowed, for Motion and for the Auto trigger key. Settings files that still select Middle load it as Right, in every profile. Movement runs only while the selected physical button is held.
- Provide one global **Apply Changes** action that persists the current user-editable settings and restores them on the next launch. Backend selects the model artifact and Compute configures supported runtimes. Precision remains a saved preference because the imported artifact determines its precision.
- Store user-editable settings in `app-settings.json` under app data. The local config page loads that file and writes it on Apply Changes; the backend loads it at startup and creates it with defaults on first launch.
- Keep one persisted settings profile on first launch, with up to three profiles in that same file. Users can create, clone, rename, delete, and select profiles in the local configuration page. A rising edge from the physical middle mouse button cycles the active profile once through the profiles that exist, saves it immediately, and reconfigures runtime; holding the button must not repeat the cycle.
- Keep movement limited to fresh target deltas, the selected held-trigger gate, recoil added to Y, and the verified Medius relative-move APIs. Do not expose or run reconstructed active-state, mode-predicate, direct-offset, or timed-click branches without their source state producers and algorithms. Auto's separate target-valid timing state may issue its explicitly configured left-click action through the verified vendor APIs.

HTTP/network save failures are errors; browser caching must never turn a failed disk write into a successful save. Keep profile saving separate from loading after deletion so surviving snapshots are preserved.
- Keep the Preview empty state visible above its canvas when no frame has arrived; label it “NO FRAME” and show the appropriate startup or sender-waiting status.

## Architecture boundaries

- Keep application/runtime logic in Rust: a native Slint host (supervision, Medius I/O, movement, receiver rendering), a Leptos/WASM settings page, and the Rust backend sidecar. Embed the backend and config assets in one portable SysX.exe. No browser/WebView dependency belongs in the receiver. Trunk builds only the separate config page.
- Build the config UI with Trunk through `scripts/build-rust-ui.mjs`; the native host does not load that bundle, while `web_config.rs` serves it at `/config.html` for the separate loopback browser page.
- Keep frame acquisition, processing, persistence, and rendering decoupled.
- In the Rust runtime, keep packet reassembly in `rust-backend/src/udp.rs`, UDP/JPEG receive in `receiver.rs`, crop geometry in `crop.rs`, model runtimes in `inference.rs`, processing in `pipeline.rs`, movement in `movement/`, and local web config in `web_config.rs`. UDP is the only production frame source.
- Keep target selection and mouse output as a post-detection stage. Pixel Seek consumes its mask; Object Detection applies score gates and the reconstructed center-ellipse, nearest-box, prior-box coverage, and class anchor rules. Port reconstructed formulas only where their runtime inputs map to current settings/state; do not fabricate missing class groups, feature flags, or state producers.
- Keep the Auto feature isolated in `src-tauri/src/auto.rs`; its explicit left-click timing state remains separate from `movement.rs` and is fed by the backend's center-crossing `auto_target_valid` event.
- Keep Auto timing values in milliseconds. Auto searches valid targets only inside its FOV circle; while the trigger is held, a target passing through the screen center (`auto_target::has_target_at_center`: a mask pixel in the center cells or, because the game's crosshair hides the center and its arms hide the center row and column, mask pixels inside the FOV on all four sides of the center — left, right, above and below, on any rows/columns) arms one delayed click. A crosshair dot can be larger than the Auto FOV and hide every target pixel inside it, so `auto_target::CrosshairTracker` measures it from the original (unfiltered) image: within a 96 px window around the center, on frames where at least half of the window border changed (the scene moved), each pixel's change rate is averaged (EMA 0.02); pixels changing in under 10 % of those samples are the overlay, and the radius is the second shortest static run along the four diagonals (which miss the arms), after 30 samples. The four-sides search then reaches max(Auto FOV radius, crosshair radius + 3 px); 0 (no evidence, still scene, no crosshair) leaves the FOV radius. The `auto held` line reports the measured crosshair radius. Crosshair lines through the center plus the JPEG color bleed beside them can hide a small target for the whole time it is on center, so `auto_target::CenterCrossing` also counts a pass in time: a target straddling the center row seen west-only and then east-only within 100 ms (or straddling the center column, north-only then south-only) passed the center. Any on-center result (cells, four sides or a pass) stays valid for 30 ms so the host's few-ms polling sees it; the state resets whenever Auto is inactive. Once Delay starts, target loss does not cancel it and additional crossings do not restart it or queue more clicks. The click presses the left button for 25–40 ms (drawn per click) before releasing it: a press and release sent back to back can land in one mouse report and never reach the game. Diagnostics log one `auto held` summary line (frames, on-center frames, Auto FOV) at most every 2 s while the Auto trigger is held, and one line per click sent. Trigger release, disabling Auto, or changing its timing cancels everything that follows: a pending click and the cooldown. After a click, target loss rearms the cycle. Cooldown starts when the click command is emitted and survives target loss; Sleep only spaces Auto polling without extending the firing interval. Auto configuration controls reach the host independently of frames, invalidate old targets, and increment a revision that cancels pending clicks even across rapid disable/re-enable or trigger changes.

- Keep crop-target conversion and short-window delta aggregation in `rust-backend/src/movement/mod.rs`; the Rust service supplies each processed target. The native host's pending-delta merge, freshness check, trigger mapping, and per-command clamp live in `src-tauri/src/movement.rs`; discard any pending delta older than 100 ms before merging it with a new one. Native device monitors own vendor API calls.
- Smoothing is a strength from 1 to 50 per axis with a Min and a Max (user request): each new track (after target loss or a pipeline reconfiguration) draws a strength uniformly in [Min, Max] per axis and keeps it for the track (alpha = 1/strength; older `smoothingAlphaX/Y` migrate to min = max = 1/alpha). Motion divides its speed by that strength while the target is inside the Smooth FOV; Object Detection Preview still shows the exponentially smoothed `smoothed_target_xy`, Pixel Seek marks the raw target pixel.
- Run detection on the whole processed image independently from FOV. Filter only candidates passed into later targeting logic by the centered FOV circle. Pixel Seek masks the whole frame but yields exactly one target per frame: the topmost accepted mask pixel inside the FOV (re-searched every frame), and only the blob containing that pixel is reported/drawn. Other colored regions, including anything outside the FOV, are masked but not reported (user requirement). Target lock (anti-flip, both engines): Pixel Seek keeps the previous target blob for 100 ms and searches only its box grown by max(12 px, 50 % of its larger side) inside the FOV, so higher pixels next to the target are still climbed while another target elsewhere in the FOV is ignored; when nothing remains there it falls back to the topmost FOV pixel. Object Detection keeps its reconstructed prior-box lock (same class, >50 % overlap, switch only if a new box is ~3x closer to center).
- Motion is the Normal logic from the user's `normal_1.py` (`rust-backend/src/movement/normal.rs`; user request, replacing the earlier calibrating controller, whose speed learning was slow and then jerky): once per new frame (the 4 ms ticker sends nothing for a frame it already acted on) it moves error × speed per axis (persisted `motionSpeedX/Y`, 0.01–1, default 0.045), divided by the track's smoothing strength while the target is inside the Smooth FOV (`smoothFovDegrees`, 1–360, default 20, same degree scale as the Motion FOV), converted to counts with the in-game sensitivity (`counts_per_px = 1 / (sens × 1.0)`; px per count really depends on the game's yaw, FOV and capture resolution, so Speed absorbs the rest), with fractional counts carried to the next frame (dropped on reversal) and a 1 px dead zone. Nothing is learned and nothing is saved; the backend deletes the old `motion-calibration.json`. The original's forced ±1 step for errors ≥ 3 px is left out (re-sent every frame before the first shows, it made the aim hunt in simulation). No WindMouse, Bézier, NCAF or random drift in this mode. Speed per frame is limited by latency: `normal_report` (ignored test; closed loop at 240 FPS, latency split 60/40 between capture and command, px/count off by ×0.5/1/2, still target 60 px away) at 0.045 reaches within 3 px in 0.22/0.18/0.12 s at ×1 for 16/30/50 ms with ≤ 4 px overshoot, and stays stable up to 50 ms at ×2 (38 px overshoot); 0.06 diverges at 50 ms × 2 and 0.1 at 50 ms × 1. Simulation only. Backend and native pending queues sum fresh deltas before API output; stale targets expire after 100 ms and each axis is clamped to ±32 device units per command; the part of a target delta beyond the clamp goes back into the pending queue for the next command (clipped recoil does not). Host and backend request 1 ms Windows timer resolution at start (`native-shared/timer_resolution.rs`: `timeBeginPeriod(1)` plus the power-throttling opt-out); the host's `role=host` socket reads with a 2 ms timeout so trigger changes reach the backend within about a tick. There is no DPI setting (older settings files with `dpi` still load and drop it on the next save).
- Auto (`tests/auto_ads.rs`, real color mask, center cells and host `AutoState`; assumed 16 ms capture→backend, 4 ms host tick, 8 ms click→game) at 2/2.5/3.5/5×: a solid-colored target is zoom-independent (100% at 100 px/s; 0% at 250 px/s for a 6 px head because its 24 ms dwell is shorter than the 28 ms reaction, at every zoom). A fixed 2 px outline at 250 px/s is missed between frames as zoom grows (crossings hit 100/80/40/30% at 2/2.5/3.5/5× from the start); with Cooldown 0 the exit-edge click of an outline lands off the body (about half the shots). Simulation only.
- Movement output uses the type-0 `SerialCommandQueue` in `src-tauri/src/serial_queue.rs`. A `ThreadedSerialWriter` invokes the Medius Rust SDK adapter on a cloned `Device`, keeping button telemetry independent of writes. `[M, dx_le, dy_le]` and `[C]` are internal work records, never device wire frames. Take targets only when the queue is idle; retain bytes until completion and preserve fresh-delta aggregation. SDK-managed I/O timeouts apply; `request_ms` is a forwarded writer hint, not a queue-enforced cancellation deadline or device acknowledgement.
- Use bounded queues and discard obsolete frames when processing falls behind.
- Preview must show every input frame (user requirement: preview FPS = input FPS). The backend wakes each preview socket per processed frame through a `tokio::sync::watch` channel (never timer polling: Windows timers tick at ~15.6 ms and capped Preview near 60 FPS), forwards the sender's original JPEG without re-encoding, shares processed frames as `Arc` (no image copies), and `state()` must not block on the UDP source lock (it reads `SourceView`). The page decodes with `createImageBitmap` off the main thread. With a 240 FPS libobs source (headless, 2026-10-15) the monitor page received 230.3 and drew 229.7 frames/s; a raw WebSocket client received 224.8 frames/s. Visible frames are still limited by the monitor's refresh rate. The HUD `ms` is `total_processing_ms`: the per-frame detection time (crop → detect → target choice), excluding network, JPEG decode, and drawing.
- Keep source, inference, and display resolutions distinct. Preview scaling must not alter detection input.
- Keep preview fitting, detection-box mapping, and HiDPI backing-size math in pure helpers in `rust-ui/src/layout.rs` with Rust unit coverage.
- Keep Preview confidence filtering in a pure helper with regression coverage for the threshold boundary, missing confidence, and Pixel Seek bypass.
- HUD FPS and latency numbers are colored green/amber/red (user-specified) via the tested pure helpers in `rust-ui/src/layout.rs`: `fps_tone` compares processing FPS with the measured input (source) FPS (≥ 80 % green, ≥ 50 % amber, below red); `latency_tone` uses a fixed 0–10 ms scale for every input rate (< 4 ms green, < 7 ms amber, ≥ 7 ms red), and above `LATENCY_HIGH_MS` (10 ms) the HUD adds a red "(HIGH)" tag. No color without measurements.
- The HUD FPS is processing FPS (user-confirmed). Preview FPS is a goal, not a HUD readout: Preview must keep up with the input FPS; no preview-FPS counter is computed in the page. Source FPS is valid decoded frames observed by the receiver over a trailing one-second window; processing FPS is completed detections over a trailing one-second window. The processing completion-time deque holds 4096 samples and has a regression test above the requested 360 FPS range; update its capacity and test together if the supported rate rises beyond that window's capacity.
- The config page only edits and saves settings (user request): the backend sends preview frames to `role=monitor` sockets only, never to the config page or the host, so it shows no runtime readouts such as the actual inference device. The monitor draws each frame once: detections/target are updated untracked so only the `frame` signal wakes the redraw, 100 ms state updates only notify when a value changed, one `createImageBitmap` decode runs at a time (newer frames mark the canvas dirty and the newest is drawn next), and the canvas backing store is resized only when its size changes.
- Keep browser configuration controls keyboard-visible and provide at least 24 CSS px pointer targets for compact switches; configuration controls must remain keyboard accessible.
- Apply boxes and labels in display coordinates after scaling the source image.

## Data and safety

- Never fabricate FPS, latency, detections, model metadata, or benchmark results.
- Keep any synthetic Pixel Seek microbenchmark explicitly separate from production color profiles and end-to-end performance claims. No current Rust benchmark is available; historical Python benchmark figures are not Rust performance evidence.
- Retain a backend integration test that changes the UDP port, confirms the new bind, and processes a frame on the new port.
- Use `src/assets/red-cube-192.jpg` as the actual JPEG fixture for sender protocol smoke checks; preserve its SOI/EOI markers.
- After adding SOI/EOI validation during UDP reassembly, 3-second 1280×720 synthetic runs measured 179.88/179.96/179.87 sender/source/processing FPS at the 180 target and 359.96/360.06/359.79 at the 360 target, with 0 skipped sender slots, input drops, transport drops, invalid packets, or rejected frames and 181 preview messages per run. This remains backend-only synthetic evidence.
- Include requested sender FPS, measured source FPS, processing FPS, preview FPS, and available sender/receiver drops in benchmark reports.
- Measure the live Tauri preview separately from synthetic backend runs; report the OS, input fixture, requested/measured rates, and available drop counters for each.
- Never download or substitute a model for the user's own model.
- Validate every network packet, dimensions, chunk count, payload length, and aggregate memory before allocating or decoding. Check JPEG SOI on chunk 0 and EOI on the final chunk before retaining those payloads; discard any partial assembly if a boundary marker is invalid. UDP image payloads must be complete JPEG frames; do not accept PNG or other formats through the production sender path.
- Preserve AI class IDs exactly. Pixel Seek confidence is null unless a probabilistic metric is separately implemented.
- Do not silently resize UDP frames for Object Detection. Report and count model-resolution mismatches.
- Removing a registry model must preserve its imported model bundle files. Fall back to Pixel Seek only when the active model is removed.
- Persist data without blocking frame processing; report storage failures. `apply_settings` applies every command in the batch even when one fails (for example a busy UDP port) and reports each failure as `command: error`.

### Release hardening

- Keep release hardening separate from vision, targeting, movement, and queue logic. The native release profiles retain full PDB debug information (`debug = 2`, `strip = "none"`) at the user's request and use LTO; Windows also enables Control Flow Guard; debug/test builds must remain debuggable.
- The Windows release-only debugger guard lives in `rust-backend/src/security.rs` and `src-tauri/src/security.rs`. Do not add debugger checks to debug/test builds or alter runtime behavior in those builds.
- Keep the Windows release packaging fail-fast: `src-tauri/build.rs` must reject a missing backend sidecar or missing Trunk bundle instead of producing a non-runnable host.
- `src-tauri/build.rs` embeds the backend and UI into one host executable. When VMProtect is used, protect the backend before embedding it, then protect the final `SysX.exe`; protecting only the outer host leaves the extracted backend exposed at runtime. ## Backend notes

- Backend modules and regression tests live in `rust-backend/src` and the Rust crate tests. Do not restore the removed Python backend.
- UDP v1 uses the bounded `RCVR` chunk protocol in `rust-backend/src/udp.rs`. Keep each datagram at or below 1200 bytes, validate metadata before retaining payloads, cap frame/reassembly memory, expire incomplete frames during socket-idle timeouts as well as while packets arrive, and preserve latest-frame semantics. Reject completed frames older than the last `(timestamp_ns, frame_id)` pair; reset ordering for a changed sender endpoint or one second without valid chunks. UDP v1 still supports only one active sender.
- The receiver reads every datagram already queued (non-blocking drain, bounded) before it decodes, and decodes only the newest complete frame: when JPEG decoding falls behind (weak machines; decode dominates per-frame cost, about 4.6 ms for a noisy 640 × 640 JPEG on a 4-core cloud VM versus ≤ 0.8 ms for mask, Pixel Seek or Color Filter), the 8 MiB socket buffer otherwise held seconds of old frames and Motion chased them. Each `SourceFrame` carries `received` (frame complete at the receiver); movement samples carry that age, so the ticker's 100 ms freshness and its time-since-capture estimate include decode and processing time.
- JPEG decoding (backend frames as RGB, native Preview as RGBA) goes through libjpeg-turbo in `native-shared/jpeg.rs` (user request; `turbojpeg` crate, static vendored build with `require-simd`, so CMake and NASM are build prerequisites). It reads the header and rejects a size other than the declared one before allocating pixels (max side 8192). Measured on a 4-core cloud VM (release build): 640 × 640 frames decode in 1.40 vs 1.57 ms (34 KB JPEG) and 3.77 vs 4.79 ms (274 KB) against the previous `image`/zune-jpeg decoder; 256 × 256: 0.26 vs 0.28 ms and 0.58 vs 0.75 ms. Not a measurement on the user's machine.
- The receiver thread only reassembles; `decode_pool::DecodePool` decodes on 1–3 workers (one per two logical CPUs) so decoding overlaps reassembly and successive frames. Only the newest waiting frame is kept and a frame finishing after a newer one is dropped (both counted in `transport_dropped_frames`; corrupt JPEGs in `invalid_frames`), so frames reach the pipeline in order. UDP `ConnectionReset` (Windows reports an ICMP port-unreachable for an earlier SYSCFG that way) leaves the socket usable and is ignored instead of closing the listener for the 3 s retry.
- Retry frame-source socket errors every 3 seconds. Drop and count corrupt JPEG/dimension-mismatch frames without closing the listener. Keep the current listener active while a requested replacement port is unavailable; once it binds, update runtime state and clear the recovered error.
- Rust `LatestFramePipeline` must stay bounded and discard a result if strategy configuration changed while it was processing.
- Do not persist per-frame detection results: the former `storage.rs` JSONL log grew about 290 MB per hour at 240 FPS and was never read. The backend deletes the `sessions` folder older versions left in app data at startup. Persist settings and calibration only, outside the processing worker, and surface storage failures.
- The Rust `udp-send-image` and `udp-listen` CLI commands are local protocol verifiers, not a production sender or a substitute for desktop integration.
- The OBS plugin follows `docs/OBS_RECEIVER_PROTOCOL.md`; keep that document, `rust-backend/src/udp.rs`, `rust-backend/src/receiver.rs` (SYSCFG), and `obs-plugin/sysx-canvas-sender` aligned.
