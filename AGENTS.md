# Project instructions

> **Current availability:** Pixel Seek and Object Detection are both selectable (Object Detection unlocked 2026-10-24 at the user's request). Object Detection and its ONNX Runtime, OpenVINO and TensorRT integrations have **not been validated** with a real model, runtime or game; build and unit-test results are not functional validation. SysX supports **Medius only** through its Rust SDK.

## Current source status

The active SysX desktop source is Rust (`rust-backend`, `src-tauri`, and shared pure-Rust helpers in `rust-ui`). Preview and configuration are native Slint windows in `src-tauri/src/monitor_window.rs`, with bounded authenticated IPC/JPEG workers in `native_monitor.rs`. Preserve the existing monitor design; do not introduce Win32/GDI controls, egui, WebView2/Wry or a browser fallback. Configuration exists only in the native app; do not restore `/config.html` or `/monitor.html`.

- The product name is **SysX**. Use SysX in user-facing UI, window metadata, and current product documentation. Preserve internal identifiers and settings storage keys unless migration is explicitly required.

## Product direction

- Support Windows and macOS native desktop releases, not an installer or browser-hosted website: Windows ships as one portable `.exe`, macOS as a native `.app`. Each host embeds the Rust backend and extracts it under platform app data (`runtime/`), then opens native Preview/Settings windows. Since 2026-10-31 (user report: slow startup; the backend carries the built-in models, about 200 MB) the extracted backend stays between launches and is rewritten only when `runtime/receiver-backend.stamp` does not match the build's content hash (`EMBEDDED_BACKEND_HASH` from `src-tauri/build.rs`); likewise `models/builtin/.stamp` (`EMBEDDED_MODELS_HASH` from `rust-backend/build.rs`) lets the backend skip reading the model files back when only their length needs checking.
- Keep the English UI dark, minimal, and technically professional.
- Receiver visual system: simple single-page dark Preview surface with near-black blue background, a large feed, compact in-feed HUD plate, operational green for healthy/live state, amber for waiting, red for errors, and monospace only for measured data. Keep navigation out of the monitor page. Preserve high-contrast text and restrained motion; the persisted source of truth is `design-system/sysx-native-receiver/MASTER.md` and the Slint component in `src-tauri/src/monitor_window.rs`.
- Keep the native receiver focused on Preview, device/connection status, active profile and five-button Mouse State. Put configuration in a separate native Slint Settings window. Closing the monitor hides it and closes its preview connection; an open Settings window keeps the backend alive, otherwise exit after a 3 s grace period. A second launch focuses the native window or signals `Local\SysX.NativeMonitor.Show` to reopen it. The backend exits when the owned host connection closes. No browser fallback belongs in the receiver lifecycle. On Windows the launched `SysX.exe` is a small supervisor (`src-tauri/src/supervisor.rs`, user request): it runs the app as a child (`SysX.exe --supervised`) and starts it again 2 s after it ends with any exit code but 0 (a crash, the backend dying, a kill), at most 5 times a minute; the app exits 0 only when the user closed it or another SysX was already running. The app smoke launches with `--supervised`. A Slint event-loop error that no quit request caused (a draw/resize failure such as a lost OpenGL context) must not close SysX: `monitor_window::run` destroys and recreates the visible windows and re-runs the loop, giving up after 5 errors in 10 s.
- Color Filter (persisted `colorFilter`, per profile; toggle in the Main card's Modules group below Motion, Auto and Recoil; `set_color_filter` command): when on, the pipeline blacks out every pixel outside the selected Pixel Seek color profile *before* Motion, Auto (and Object Detection) process the frame (`pixel_seek::color_filtered`), so both see only the selected color. Preview shows that same filtered image without re-encoding: the frame message carries the applied mask packed one bit per pixel (pixel `i` = bit `i % 8` of byte `i / 8`, `color_mask` metadata) between the metadata and the original JPEG, and the native decode thread blacks out the unset pixels. Toggling reconfigures the pipeline. Because the filter uses the same profile as Pixel Seek, its targets are unchanged; the filter adds one mask and image-copy pass to processing time.
- Render the five Mouse State buttons at equal width so Left, Right, Middle, M4, and M5 read as one aligned group.
- Keep the Preview viewport square and cap it at 640 × 640 CSS pixels. Smooth scaling should enlarge small sender frames while preserving aspect ratio; Pixel Perfect should use nearest-neighbor interpolation.
- Keep a circle-only FOV overlay always enabled; let the user set it from 1–360° in native Settings. Map degrees to pixels against a fixed 640 px reference (`FOV_REFERENCE_PX` in `targeting.rs` and `rust-ui/src/layout.rs`: 360° = 640 source px, limited to the image), not the crop side: the crop is a native-resolution cutout, so the same degree setting is the same circle on screen at every Crop Resolution (user request). Do not add an enable/disable control.
- Let native Settings scroll vertically as additional options are added. The desktop Preview is always visible and its HUD shows only processing resolution, FPS, and latency.
- Keep native Settings compact, readable and keyboard accessible. Each section (Profiles, Detection, Motion, Magnet, Recoil, Connection) is its own page chosen from the left rail; since 2026-10-31 (user request, modelled on screenshots the user supplied) each page is one card of grid rows: label above the control and an optional hint below, dropdowns with a popup list, sliders (drag or ←/→; the value commits on release), two engine radio cards, an offset pad and Short/Medium/Long booster sliders; a smoothing Min dragged past its Max moves the Max along (and the reverse) (user request: separate pages, not one long page with jump links); the Motion, Magnet and Recoil on/off switches for the active profile live only in a Modules row on the Profiles page (user request, 2026-11-01), not on their own pages; a page scrolls if it outgrows the window, and the header profile pill plus the footer status and one Apply Changes action stay on every page.
- Show signed X/Y target offsets in crop-pixel units with a compact 2D indicator: the center cross is the selected target and the white marker is the configured destination relative to it. Persist/apply offsets with the global settings action.
- Provide a persisted Trigger button setting in native Settings with exactly Right, M4, and M5 choices; Left (fires) and Middle (cycles profiles) are not allowed, for Motion and for the Auto trigger key. Settings files that still select Middle load it as Right, in every profile. Movement runs only while the selected physical button is held.

## Architecture boundaries

- Keep application/runtime logic in Rust: a native Slint host (supervision, Medius I/O, movement, Preview and Settings), plus the Rust backend sidecar. Embed the backend in the Windows executable and macOS app bundle. No browser/WebView or Leptos/WASM configuration dependency belongs in the product.
- Keep frame acquisition, processing, persistence, and rendering decoupled.
- In the Rust runtime, keep packet reassembly in `rust-backend/src/udp.rs`, UDP/JPEG receive in `receiver.rs`, crop geometry in `crop.rs`, model runtimes in `inference.rs`, processing in `pipeline.rs`, and movement in `movement/`. Native Settings talks to the backend through its authenticated host IPC. UDP is the only production frame source.
- Keep target selection and mouse output as a post-detection stage. Since 2026-10-31 (user request: "update new logic" from the user's `source/rust/src/{pixel_seek,motion,target_manager,unified_engine}.rs`, replacing the earlier logic outright) both engines feed `rust-backend/src/target_manager.rs`: detections associate greedily with the nearest tracked entity within 60 px, matched entities update an EMA velocity (alpha 0.40), unmatched ones stay where they were last seen for up to 140 ms without prediction (since 2026-10-31, user report of the aim drifting off the target: while Motion turns the camera the on-screen velocity is mostly that turn), matched ones move to an EMA of their box (`POSITION_ALPHA` 0.6, position and size) so box noise does not shake the aim, and selection takes the entity center closest to the crosshair inside the FOV with a 38 px bonus for the locked one. The lock is released whenever no Motion/Auto action holds it. Since 2026-10-31 (user request: support the class layouts of the models they use, head first) class roles come from the model's own Ultralytics `names` metadata (`targeting::class_role`): a name with a word such as teammate/tm/ally, utility/flash/smoke/fire/grenade, weapon/gun, dead/corpse or third/self is ignored, `ability`/`abilities` is an ability, `head` a head, anything else a body; a model without names keeps the source's fixed classes (1 head, 3 ability, 2 and 4 ignored). Abilities (user request) are valid targets with their own Min ability confidence (`abilityConfidence`, per profile, 0–1, default 0.6, Detection page; the decoder keeps boxes down to the lower of the two thresholds) and are aimed at their center. Ignored classes, boxes under 2 × 2 px and boxes below Min confidence (the source's fixed 0.30 is replaced by Min confidence) never reach the target manager. Heads and other classes are tracked separately (a head never continues a body track), and selection ranks head, then body, then ability (`TargetKind`): a body is chosen only with no head in the FOV, an ability only with neither; the 38 px hysteresis applies within the same kind. A head box is aimed at its center, any other box 15 % below its top (`targeting::aim_point`). Claude declined to copy the model-specific settings from the user's screenshots of the CapkfaPlus UI (Side for the CS2 model, Min Ability/Flash Confidence, Flash Dodge, Color Swap, its model display names). The former class-rank priority, center-ellipse and prior-box lock were removed.
- Keep the Auto feature isolated in `src-tauri/src/auto.rs`; its explicit left-click timing state remains separate from `movement.rs` and is fed by the backend's center-crossing `auto_target_valid` event.
- Magnet (user request, 2026-10-31, from the user's `magnet.rs`; persisted `magnet`, per profile; own Settings page laid out like Motion): while its trigger (Right/M4/M5, default M5) is held, the host's `src-tauri/src/magnet.rs` plans moves and separate left press/release records (`D`/`U` in `serial_queue.rs`) from the backend's per-frame `magnet_target` event (error in crop px with Magnet's own `offsetX/Y`, `counts_per_px = 1/sens`; older than 100 ms counts as Magnet off and releases the button; the device loop releases a Magnet-held button when it ends). Magnet has its own FOV (`fovDegrees`) and Dynamic FOV (`dynamicFovDegrees` while `dynamicFovKey` is held, `off` by default); a held Magnet trigger selects targets in that FOV. Modes: `spray`, `tap`, `silent_immediate` ("Flick") and `auto` (user request: Auto is now a Magnet mode; it drives the unchanged center-crossing `auto.rs` through `AppSettings.auto`, which `validate()` and profile snapshots derive from Magnet; files saved before this keep their Auto trigger/FOV/timing as Magnet's and select `auto` when Auto was on). Since 2026-11-01 (user request: "tap fires one bullet, spray a few, flick flicks fast and snaps back"; each press must find the target in the FOV within a frame and pull to it at once) each press of the Magnet trigger is one action (`src-tauri/src/magnet.rs`): on the first frame after the press with a target (the frame on screen at the press is skipped; with no target it waits while held) it snaps onto the target, the whole error at once through the source's `pixel_to_counts`, px / (sens × 0.022 × 3.125) (Claude noted this is about 14.5× the `1 / sens` that Motion uses, since the source treats 1 px as 1°; the user chose the source), then `tap` fires one shot, `spray` holds the button for a burst of up to `forcedReleaseMs` ("Max burst", default 250) pulling every new frame by error / smoothing (drawn in [`smoothX/YMin`, `smoothX/YMax`], px sent as counts like the source) × the speed booster and releasing early on target loss, `silent_immediate` ("Flick") fires one shot and moves back by the snap, and `auto` fires one shot while `auto.rs` keeps its center-crossing clicks. A shot holds the button 25–40 ms, drawn per shot (a press and release sent back to back can land in one mouse report). Holding the trigger does not repeat the action. Delay, Cooldown and Sleep are shown and used for Auto only; Hold (`fireHoldMs`), Tap interval (`resetTimeoutMs`), Snap back (`snapBack`), `silent_proximity` ("Silent flick (near)") and `flickProximityPx` were removed (older files load them and drop them; `silent_proximity` becomes `silent_immediate`). Magnet samples are sent in every mode; under Auto, which publishes no Motion target or reticle, the Pixel Seek path still clusters and tracks, and the head point travels separately as `ProcessedFrame.snap_target`, which `magnet_event` uses. Not validated in game.
- Auto has one mode, Center crossing (below). The Aim + fire mode (`movement/flick.rs`) was removed on 2026-10-18 at the user's request; settings files that still carry `auto.mode`, `auto.speedX/Y`, `auto.smoothing*`, `auto.smoothFovDegrees` or `auto.offsetX/Y` load and drop them on the next save.
- Keep Auto timing values in milliseconds. Auto searches valid targets only inside its FOV circle; while the trigger is held, a target passing through the screen center (`auto_target::has_target_at_center`: a mask pixel in the center cells or, because the game's crosshair hides the center and its arms hide the center row and column, mask pixels inside the FOV on all four sides of the center: left and right within `CENTER_BAND_PX` 4 px (or the measured crosshair radius + 3 px) of the center row, above and below within that distance of the center column; user report 2026-10-18: with any rows/columns, two separate strips left and right of the center that each reached above and below it fired with nothing on the center, so diagonal-only or side-only pixels no longer count; `auto_ads` figures are unchanged) arms one delayed click. The crossing check below still uses the sides on any rows/columns. A crosshair dot can be larger than the Auto FOV and hide every target pixel inside it, so `auto_target::CrosshairTracker` measures it from the original (unfiltered) image: within a 96 px window around the center, on frames where at least half of the window border changed (the scene moved), each pixel's change rate is averaged (EMA 0.02); pixels changing in under 10 % of those samples are the overlay, and the radius is the second shortest static run along the four diagonals (which miss the arms), after 30 samples. The four-sides search then reaches max(Auto FOV radius, crosshair radius + 3 px); 0 (no evidence, still scene, no crosshair) leaves the FOV radius. Crosshair lines through the center plus the JPEG color bleed beside them can hide a small target for the whole time it is on center, so `auto_target::CenterCrossing` also counts a pass in time: a target straddling the center row seen west-only and then east-only within 100 ms (or straddling the center column, north-only then south-only) passed the center. Any on-center result (cells, four sides or a pass) stays valid for 30 ms so the host's few-ms polling sees it; the state resets whenever Auto is inactive. Once Delay starts, target loss does not cancel it and additional crossings do not restart it or queue more clicks. The click presses the left button for 25–40 ms (drawn per click) before releasing it: a press and release sent back to back can land in one mouse report and never reach the game. Trigger release, disabling Auto, or changing its timing cancels everything that follows: a pending click and the cooldown. After a click, target loss rearms the cycle. Cooldown starts when the click command is emitted and survives target loss; Sleep only spaces Auto polling without extending the firing interval. Auto configuration controls reach the host independently of frames, invalidate old targets, and increment a revision that cancels pending clicks even across rapid disable/re-enable or trigger changes. (Restored 2026-10-18: the native port had replaced this with a check that the single selected topmost pixel's path passes within 0.5 px of the exact center, which almost never happens because that pixel sits above the center while a target crosses, so Center mode stopped firing.)

- Keep crop-target conversion and short-window delta aggregation in `rust-backend/src/movement/mod.rs`; the Rust service supplies each processed target. The native host's pending-delta merge, freshness check, trigger mapping, and per-command clamp live in `src-tauri/src/movement.rs`; discard any pending delta older than 100 ms before merging it with a new one. Native device monitors own vendor API calls.
- Smoothing is 1 to 50 per axis with a Min and a Max (defaults 1–1, stable): since 2026-11-01 it is stable's smoothing strength, drawn from [Min, Max] once per engagement (redrawn after the target is lost, Motion goes inactive or the range changes) and dividing the Speed only inside the Smooth FOV (`smoothFovDegrees`, default 20°), fading out toward the target along (distance / radius)³. `smoothed_target_xy` equals `target_xy`; there is no separate target smoother. Motion also has Dynamic FOV (`dynamicFovDegrees` while `dynamicFovKey` is held; `off` by default); key edges reconfigure the pipeline.
- Motion Output has only Normal and Normal + ABCurves. ABCurves captures a physical Medius mouse profile automatically when enabled and the current settings profile has no sample; Normal runs until capture is saved. ## Backend notes

- Backend modules and regression tests live in `rust-backend/src` and the Rust crate tests. Do not restore the removed Python backend.
- UDP v1 uses the bounded `RCVR` chunk protocol in `rust-backend/src/udp.rs`. Keep each datagram at or below 1200 bytes, validate metadata before retaining payloads, cap frame/reassembly memory, expire incomplete frames during socket-idle timeouts as well as while packets arrive, and preserve latest-frame semantics. Reject completed frames older than the last `(timestamp_ns, frame_id)` pair; reset ordering for a changed sender endpoint or one second without valid chunks. UDP v1 still supports only one active sender.
- The receiver reads every datagram already queued (non-blocking drain, bounded) before it decodes, and decodes only the newest complete frame: when JPEG decoding falls behind (weak machines; decode dominates per-frame cost, about 4.6 ms for a noisy 640 × 640 JPEG on a 4-core cloud VM versus ≤ 0.8 ms for mask, Pixel Seek or Color Filter), the 8 MiB socket buffer otherwise held seconds of old frames and Motion chased them. Each `SourceFrame` carries `received` (frame complete at the receiver); movement samples carry that age, so the ticker's 100 ms freshness and its time-since-capture estimate include decode and processing time.
- JPEG decoding (backend frames as RGB, native Preview as RGBA) goes through libjpeg-turbo in `native-shared/jpeg.rs` (user request; `turbojpeg` crate, static vendored build with `require-simd`, so CMake and NASM are build prerequisites). Measured on a 4-core cloud VM (release build): 640 × 640 frames decode in 1.40 vs 1.57 ms (34 KB JPEG) and 3.77 vs 4.79 ms (274 KB) against the previous `image`/zune-jpeg decoder; 256 × 256: 0.26 vs 0.28 ms and 0.58 vs 0.75 ms. Not a measurement on the user's machine.
